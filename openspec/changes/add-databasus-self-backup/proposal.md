# Proposal

## Why

Когда сервер Databasus умирает, вместе с ним пропадают все настройки: пользователи, воркспейсы, подключения к базам, хранилища, нотификаторы, расписания и история бэкапов. Бэкапы в хранилищах при этом целы, но без внутренней базы логические дампы приходится расшифровывать вручную, а физические бэкапы на практике не восстановить. Перенести Databasus на другой сервер сейчас можно, только скопировав папку `databasus-data` целиком.

Ключ шифрования к тому же нигде не предлагают сохранить. Если его нет, не поможет даже бэкап внутренней базы.

## What Changes

- **Хранилища инстанса.** Хранилище принадлежит либо воркспейсу, как сейчас, либо инстансу. Хранилищами инстанса управляют только администраторы. У такого хранилища две независимые роли: принимать бэкапы самого Databasus и быть доступным воркспейсам для бэкапов их баз (никому, всем или выбранным воркспейсам). Участники воркспейса видят у него только имя и тип.
- **Хранилище инстанса из воркспейса в один клик.** Администратор обычно уже заводит S3 в воркспейсе. Чтобы бэкап Databasus уходил за пределы сервера без повторного ввода credentials, в форме создания хранилища есть галочка «использовать и для бэкапов Databasus», а у существующего хранилища воркспейса — такое же действие. Хранилище становится хранилищем инстанса, а воркспейс сохраняет к нему доступ. Обе возможности есть только у администраторов инстанса, обратного перевода нет.
- **Хранилище инстанса на диске сервера по умолчанию.** Новый и обновлённый инстанс сразу получает LOCAL-хранилище инстанса для бэкапов Databasus, поэтому бэкап самого Databasus работает без настройки.
- **Бэкап самого Databasus.** По расписанию и по кнопке «Сделать бэкап сейчас» Databasus снимает дамп своей внутренней базы, шифрует его ключом и кладёт копию в каждое хранилище инстанса, отмеченное для бэкапов Databasus. Секция в глобальных настройках показывает список бэкапов с состоянием копий, кнопку скачивания, расписание и retention. Неудачный запуск повторяется через 5 минут, до трёх попыток подряд, поэтому короткий сбой хранилища до администраторов не доходит. Если копия в хранилище не записалась три раза подряд, администраторы видят предупреждение и получают одно письмо, если на инстансе настроена почта, и ещё одно, когда хранилище снова заработает.
- **Восстановление на новом сервере.** На пустом инстансе экран первого запуска предлагает не только создать аккаунт, но и восстановить Databasus из бэкапа, загрузив его файл. Хранилища при этом не подключаются: файл скачивают из глобальных настроек старого инстанса или из хранилища средствами провайдера. То же можно сделать без интерфейса, через переменную окружения. Ключ проверяется до восстановления, а бэкап из более новой версии Databasus отклоняется. Перед восстановлением экран предупреждает, что старый инстанс нужно выключить: иначе оба будут писать в одни хранилища и удалять файлы друг друга. После восстановления инстанс сразу работает как обычно.
- **Замена данных работающего инстанса.** Root admin может восстановить инстанс из бэкапа Databasus прямо в секции бэкапов, загрузив его файл: например, если на новом сервере успели зарегистрироваться до восстановления, или для отката. Текущая база удаляется и заменяется бэкапом одной транзакцией, поэтому битый файл оставляет прежние данные. Отменить замену нельзя, путь назад — заранее скачанный бэкап этого инстанса, и предупреждение перед заменой об этом напоминает. Пока идёт замена, интерфейс показывает индикатор восстановления.
- **Передача ключа.** Root admin один раз видит ключ шифрования и подтверждает, что сохранил его: после регистрации или, на уже работающих инстансах, после обновления. После этого ключ доступен только на сервере.

## Capabilities

### New Capabilities

- `instance-storages`: хранилища, которыми владеет инстанс, их роли, права доступа и хранилище по умолчанию на диске сервера.
- `databasus-self-backup`: бэкап внутренней базы Databasus в хранилища инстанса, расписание, retention, список, скачивание и уведомления.
- `databasus-recovery`: восстановление Databasus из его бэкапа на пустом и на работающем инстансе, проверки ключа и версии, предупреждение о старом инстансе и обработка состояния, которое не переносится.
- `secret-key-handover`: однократный показ ключа шифрования root admin.

### Modified Capabilities

- `container-shutdown`: на код выхода восстановления контейнер снова запускает приложение, не останавливая встроенный PostgreSQL.

Требования `root-admin-account` остаются в силе: пустой инстанс по-прежнему предлагает создать аккаунт, а восстановление добавляется рядом и описано в `databasus-recovery`.

## Out of scope

- Страница «Как восстановить без Databasus» и правки в ней.
- Копии бэкапов пользовательских баз в нескольких хранилищах (3-2-1) и S3 Object Lock.
- Сверка каталога бэкапов с хранилищами после восстановления: импорт бэкапов, сделанных после снимка, и пометка отсутствующих файлов.
- Хранилища инстанса для нотификаторов и нотификаторы уровня инстанса.
- Отдельный retention для каждого хранилища и копирование бэкапов Databasus между хранилищами.
- Пробное восстановление бэкапа Databasus.
- Ротация ключа шифрования.
- Режим паузы после восстановления и отмена замены данных.
- Квоты и отдельные префиксы для воркспейсов в общем хранилище инстанса.

## Impact

- Модуль backend, правила `backend/AGENTS.md`: хранилища (владелец, роли, доступ воркспейсов), новая фича бэкапа Databasus, запуск приложения (восстановление до миграций), пользователи (показ ключа root admin).
- Модуль frontend, правила `frontend/AGENTS.md`: секция бэкапов Databasus и хранилищ инстанса в глобальных настройках, выбор хранилища инстанса в настройках бэкапа базы, экран восстановления при первом запуске, экран ключа, предупреждение перед восстановлением и предупреждения о сбоях.
- Docker-образ: `docker/start.sh` перезапускает приложение после восстановления, не останавливая PostgreSQL.
- Документация на сайте, правила `website/AGENTS.md`: FAQ перестаёт советовать бэкапить `databasus-data` вручную и описывает встроенный бэкап и восстановление на всех шести языках.
- Новый ADR: восстановление Databasus через `pg_dump` внутренней базы и существующие миграции, с исключением из ADR-0004 для загруженного файла бэкапа, который ждёт перезапуска на диске.
- **BREAKING:** колонка `workspace_id` у хранилища становится необязательной. Код, который считает, что у каждого хранилища есть воркспейс, переписывается. Обёрток для старого поведения не остаётся.
