# Design

## Context

Мотивация описана в proposal.md, раздел Why. Здесь только состояние кода, которое определяет подход.

- **Хранилища.** В Go хранилище всегда принадлежит воркспейсу: `WorkspaceID uuid.UUID` с тегом `not null` (`backend/internal/features/storages/model.go:24`). В базе колонка `workspace_id` допускает NULL: её добавили без ограничения (`backend/migrations/20251104000000_workspace_scope_storages_notifiers.sql:5`), и ни одна миграция ограничение не добавила. Права проверяет `CanUserManageDBs`, а он пускает и `WORKSPACE_MEMBER` (`backend/internal/features/workspaces/services/workspace_service.go:248-268`). Удаление воркспейса удаляет все его хранилища без подсчёта бэкапов (`backend/internal/features/storages/service.go:91-110`).
- **Учёт файлов.** `storage_files.Store` находит хранилище только по ID (`backend/internal/features/storages/file_locator.go:14-26`). Запись в каталоге — единственный учёт файла (`backend/internal/features/storages/interfaces.go:52-57`). Каждая попытка записи требует своего имени файла (`backend/AGENTS.md`, раздел «Stored files»).
- **Провайдеры** умеют только `SaveFile`, `GetFile` и `DeleteFile` (`backend/internal/features/storages/interfaces.go:13-37`), получать список файлов они не умеют. S3 пишет поток до 16 MiB одним объектом под именем файла, без манифеста. Поток больше 16 MiB уходит multipart-загрузкой с частями по 16 MiB в объект `<имя>.part000001` с манифестом `.parts`, а следующий объект `.part000002` начинается только после 1000 частей, то есть примерно после 15,6 GiB (`backend/internal/features/storages/models/s3/model.go:39-56,115-161`).
- **Пайплайн логического бэкапа** привязан к `databases.Database`, к конфигу бэкапа и к строке бэкапа (`backend/internal/features/backups/backups/usecases/logical/postgresql/create_backup_uc.go:54`). Защита встроенной базы срабатывает и при открытии туннеля (`backend/internal/features/databases/databases/postgresql/shared/embedded_target.go:23-47`). Отдельно переиспользуются шифрование `PGRSUS01` (`backend/internal/features/backups/backups/encryption/setup.go:20-45`), `StartBackgroundWrite` и `Store`.
- **Запуск.** Миграции идут первыми (`backend/cmd/main.go:92`), перенос ключа из базы в файл — после них (`backend/cmd/main.go:104`). Затем `runBackgroundTasks` безусловно запускает около тринадцати фоновых сервисов (`backend/cmd/main.go:441-514`).
- **Ключ** кэшируется в памяти на всё время жизни процесса. Если файла нет, генерируется новый ключ без предупреждения, а сам файл читается без обрезки пробелов (`backend/internal/features/encryption/secrets/service.go:52-81`).
- **Процесс.** `docker/start.sh:666-689` завершает контейнер, когда завершается приложение. README и compose задают `restart: unless-stopped`.
- **Настройки инстанса** есть только в `users_settings`, и там только политика пользователей (`backend/internal/features/users/models/users_settings.go:5-19`).
- **ADR-0004** запрещает складывать данные бэкапа на диск сервера. Исключение сделано только для `pg_restore -j`, с проверкой свободного места.

Модульные правила, которым подчиняется изменение: `backend/AGENTS.md` (разделы «Stored files», «Background services», «Migrations», «Never inject another feature's repository»), `frontend/AGENTS.md`, `website/AGENTS.md`.

## Goals / Non-Goals

**Goals:**

- Модель хранилища, которая без переделки выдержит будущие роли хранилища инстанса: копии бэкапов баз по правилу 3-2-1 и хранилища для нотификаторов.
- Одно ядро восстановления для интерфейса и для переменной окружения.
- Восстановление, которое либо проходит целиком, либо не меняет данные, без страховочных копий и режимов ожидания.

**Non-Goals:**

- Общий механизм копирования файлов между хранилищами. Бэкап Databasus пишет копии сразу при снятии дампа.
- Кластерный режим. Изменение опирается на один процесс приложения (спека `single-instance-runtime`).

## Decisions

### 1. Владелец хранилища определяется по `workspace_id`, без отдельного поля «вид»

Хранилище инстанса — это хранилище с `workspace_id = NULL`. В коде владение читается через предикат вроде `IsInstanceStorage()`, а в интерфейсе и документации называется «хранилище воркспейса» и «хранилище инстанса».

Отвергнутые варианты:

- **Отдельная колонка `kind` или `scope`.** Она хранит тот же факт второй раз, и две колонки могут разойтись. Ограничение `CHECK` их свяжет, но тогда два поля описывают одно. Если появится третий владелец, например организация, ему всё равно понадобится своя ссылка.
- **Отдельная таблица хранилищ инстанса.** Пришлось бы продублировать восемь моделей провайдеров, их шифрование и `Store`.
- **Флаг «глобальное» на хранилище воркспейса.** Участник воркспейса мог бы поменять bucket или credentials, а удаление воркспейса снесло бы хранилище вместе с бэкапами Databasus (`storages/service.go:91-110`).
- **Копия хранилища воркспейса, которую делает галочка.** Ключи пришлось бы ротировать в двух местах, а копия молча ломалась бы после ротации в воркспейсе.

### 1a. Галочка в форме воркспейса и перевод создают хранилище инстанса, а не копию

Администратор чаще всего уже заводит S3 в воркспейсе. Поэтому самый короткий путь вынести бэкап Databasus за пределы сервера — не вводить credentials второй раз. Галочка «использовать и для бэкапов Databasus» в форме создания и одноимённое действие у существующего хранилища дают одно хранилище инстанса: `workspace_id = NULL`, бэкапы Databasus включены, доступ `SELECTED` с этим воркспейсом. Перевод выполняется в одной транзакции. Конфиги, бэкапы и `StorageID` строк не меняются, поэтому бэкапы и восстановления баз воркспейса работают как раньше.

Перевод идёт только в одну сторону. Обратный перевод отрезал бы бэкапы Databasus и другие воркспейсы с доступом, а сценария, которому он нужен, нет.

Отвергнутый вариант — только глобальные настройки. Он честнее по модели, но требует повторного ввода credentials, и большинство администраторов оставили бы бэкап Databasus на локальном диске.

### 2. Роли хранилища инстанса — две независимые настройки

У хранилища инстанса есть булева настройка «принимает бэкапы Databasus» и режим доступа воркспейсов `NONE`, `ALL` или `SELECTED`. Список выбранных воркспейсов хранится в отдельной таблице связей. У хранилища воркспейса этих настроек нет, их значения ограничены через `CHECK`.

Отвергнутые варианты:

- **Enum `global / shared`.** Роли не исключают друг друга: общий бакет для воркспейсов может принимать и бэкапы Databasus. Enum вынудил бы третье значение, а будущие роли — новые комбинации.
- **Булево «доступно всем воркспейсам».** Хостерам нужен выбор воркспейсов. Переход от булева поля к списку позже был бы ломающим изменением API.

Будущая роль, например «вторичная копия бэкапов баз», добавится отдельной настройкой без изменения существующих.

Режим `SELECTED` с пустым списком отклоняется в сервисе, потому что `CHECK` не видит таблицу связей.

Владение не меняется ни одним путём. Сейчас у хранилища их три: изменение, перенос через `TransferStorageToWorkspace` (`backend/internal/features/storages/service.go:377`) и перенос базы вместе с хранилищем (`IsTransferWithStorage`, `backend/internal/features/backups/config/logical/service.go:241`, и то же в физическом конфиге). Для хранилища инстанса оба переноса отвечают ошибкой запроса, то есть HTTP 400, как другие ошибки переноса. Проверка целевого хранилища при переносе базы (`targetStorage.WorkspaceID != request.TargetWorkspaceID`, там же) заменяется общей проверкой «хранилище доступно воркспейсу». Её же используют сохранение конфига бэкапа и сам бэкап.

«Воркспейс пользуется хранилищем» означает две существующие проверки: привязанные конфиги (`GetStorageAttachedDatabasesIDs`) и бэкапы в хранилище (`GetStorageBackupReferenceCount`, `backend/internal/features/storages/service.go:216-231`), только с фильтром по воркспейсу. Отзыв доступа при оставшихся бэкапах отклоняется. При удалении воркспейса `OnBeforeWorkspaceDeletion` дополнительно убирает воркспейс из списков доступа хранилищ инстанса. Проверка «останется ли хранилище без ролей» выполняется до любых изменений, раньше удаления собственных хранилищ воркспейса (`storages/service.go:91-110`), поэтому отказ ничего не меняет. Если список пустеет, режим становится `NONE`, а если хранилище при этом остаётся без ролей, удаление воркспейса отклоняется. Отвергнутый вариант — молча оставить хранилище без ролей: это нарушило бы правило «хотя бы одна роль».

Отвергнутый вариант — разрешить отзыв и оставить воркспейсу доступ только на чтение к старым бэкапам. Тогда понадобилась бы третья, полуоткрытая форма доступа.

### 2a. Ошибки хранилища инстанса скрываются от участников воркспейса по роли читателя

Причина сбоя бэкапа (`FailMessage`) и `Storage.LastSaveError` (`backend/internal/features/storages/model.go:50-53`) хранятся полностью. DTO для пользователя без роли ADMIN подменяет их общим сообщением, если хранилище бэкапа — хранилище инстанса. Отвергнутый вариант — хранить сразу общий текст: администратор потерял бы диагностику.

### 3. Хранилище по умолчанию создаёт миграция

Одна миграция создаёт LOCAL-хранилище инстанса с включёнными бэкапами Databasus и записью в `local_storages`. Миграция выполняется один раз, поэтому удалённое администратором хранилище не вернётся без отдельного флага «уже создавали». На новом инстансе миграции тоже прокатываются, и хранилище появляется так же.

Отвергнутый вариант — создание при старте приложения. Ему понадобился бы флаг, чтобы не создавать хранилище заново после удаления. Кроме того, это вторая точка, где меняется схема данных.

### 4. Один дамп расходится по хранилищам потоком, с отключением упавшей копии

Запуск выполняет один `pg_dump -Fc` внутренней базы. Версия клиента берётся из `server_version_num` подключения, клиенты 12–18 лежат в образе. Сжатие задаётся явно, как у логических бэкапов баз (`getCompressionArgs`, `backend/internal/features/backups/backups/usecases/logical/postgresql/create_backup_uc.go:372`): `--compress=zstd:5` для PostgreSQL 16 и новее и `-Z 5`, то есть gzip, для 12–15, где у `pg_dump` нет zstd. Логика выбора выносится в общую функцию, которую вызывают оба пайплайна. Дамп сжимается внутри `pg_dump`, до шифрования: зашифрованный поток уже не сжать. Поток шифруется один раз, с `keyID`, равным ID бэкапа Databasus, и расходится по N загрузкам через `Store.WriteFile`. Если загрузка падает, она отключается от раздачи, а остальные продолжают. Обратное давление идёт от самой медленной из живых загрузок. Каждая копия подтверждается через `ConfirmFileWrites` в той же транзакции, что и её запись в каталоге.

Отвергнутые варианты:

- **Временный файл с последующей загрузкой в каждое хранилище.** Это нарушает ADR-0004.
- **Независимый `pg_dump` для каждого хранилища.** Копии были бы разными снимками, а в списке в одной строке «бэкап» оказалось бы несколько разных бэкапов.
- **Copy-after из первого хранилища.** Сбой первого хранилища ломает весь запуск, а чтение из облака — это лишний исходящий трафик.

Снимок внутренней базы держится, пока не закончится самая медленная загрузка. Для маленькой локальной базы это приемлемо. Запуск ограничен таймаутом.

### 5. Свой каталог и свои настройки у бэкапов Databasus

Новая фича в backend получает три таблицы:

- запись о бэкапе: время, размер, версия Databasus, версия схемы goose, номер попытки, время окончания, итоговое состояние и причина ошибки запуска;
- копия бэкапа: бэкап, хранилище, имя файла, состояние, ошибка и её вид;
- одна строка настроек: расписание через `intervals.Interval` и retention с теми же полями, что у бэкапов баз.

Копии регистрируют свой `StorageBackupCounter`. Поэтому обычное удаление хранилища с копиями отклоняется, а удаление с подтверждением сначала в одной транзакции удаляет записи копий вместе с `RequestFileDeletions`.

Retention считается через `gfs.GetItemsToRetain` (`backend/internal/features/backups/backups/backuping/shared/gfs/gfs.go:17`) и общие функции для политик по количеству и по времени. Расчёт retention выносится из логического cleaner в общий пакет, не завязанный на конфиг базы. Это рефакторинг затронутого кода по правилам AGENTS.md.

Файл бэкапа описывает себя сам. Он начинается с открытого блока: магические байты формата бэкапа Databasus, длина и JSON с ID бэкапа, временем, версией Databasus, версией схемы goose и major-версией PostgreSQL, с которой снят дамп. Дальше идёт обычный поток `PGRSUS01`. Так ID для `DeriveBackupKey` (`backend/internal/features/backups/backups/encryption/utils.go:31`) и версия доступны восстановлению из одного файла, даже переименованного.

Отвергнутые варианты: отдельный файл `.metadata` рядом с копией (пользователь теряет или путает его при загрузке) и ID в имени файла (файл переименовывают, а объект S3 называется `<имя>.part000001`).

Имя файла имеет вид `databasus-backup-<YYYYMMDD-HHMMSS>-<backupId>` и совпадает во всех хранилищах запуска. Уникальность имени для каждой попытки соблюдена, потому что в каждом хранилище копия записывается один раз.

Если ни одно хранилище не принимает бэкапы Databasus, планировщик запуск не начинает, а ручной запуск отвечает конфликтом с объяснением. Клиент `pg_dump` выбирается по major-версии сервера. Версия вне диапазона 12–18 даёт неудачный запуск с причиной до записи копий.

Планировщик пропускает срок, если запуск уже идёт: блокировка берётся неблокирующим advisory lock, а пропущенный срок записи не создаёт.

Повторы делает тот же планировщик, по образцу `GetRemainedBackupTryCount` логического планировщика (`backend/internal/features/backups/backups/backuping/logical/scheduler.go:191`). Запись о запуске хранит номер попытки и время окончания. Запуск по расписанию и ручной получают номер 1, повтор — номер предыдущего запуска плюс один. Прерванному запуску время окончания ставит пометка при старте. Номер попытки берётся из записи, а не из подсчёта последних неудачных запусков, как у бэкапов баз: иначе запуск по расписанию после неудачной серии не получил бы своих повторов.

На каждом тике планировщик сначала проверяет срок по расписанию. Логический планировщик передаёт в `ShouldTriggerBackup` время последнего бэкапа (`scheduler.go:254-300`), а для часового расписания это `now - last >= 1h` (`backend/internal/features/intervals/model.go:72-80`). Здесь вместо последнего запуска передаётся последний запуск с номером попытки 1, иначе серия 10:00, 10:05, 10:10 сдвинула бы следующий запуск на 11:10. Наступивший срок заменяет повтор и начинает серию заново.

Если срок не наступил, планировщик смотрит последний запуск. Повтор начинается, когда этот запуск неудачен или частично успешен, с его окончания прошло 5 минут, а номер его попытки меньше 3. Повтор не начинается, если у запуска нет ошибки запуска, а все его неудачные копии не записались из-за ошибки записи в хранилища, которые были в сбое ещё до начала этого запуска. Всё это читается из каталога, поэтому ожидающий повтор переживает перезапуск, а просроченный начинается на первом тике после старта.

Отличие от бэкапов баз — задержка в 5 минут вместо следующего тика планировщика. Короткий сбой сети или S3 за 15 секунд обычно не проходит.

Отвергнутый вариант — повторно использовать каталог логических бэкапов с особой «базой» внутри. Пришлось бы обходить защиту встроенной базы, и бэкап Databasus появился бы в местах, рассчитанных на базы воркспейсов.

### 6. Пустой инстанс восстанавливается только из загруженного файла

Экран первого запуска принимает только файл бэкапа. Хранилища он не подключает и бэкапы в них не ищет, поэтому получать список файлов провайдерам не нужно.

Файл есть у человека в двух случаях. Либо он заранее скачал бэкап из глобальных настроек старого инстанса, либо скачивает копию из хранилища средствами провайдера. В S3 копия до 16 MiB — это объект под именем файла, копия до ~15,6 GiB — объект `<имя>.part000001`. Внутренняя база Databasus крупнее на практике не бывает, но и такую копию можно склеить из объектов `.partNNNNNN` по порядку номеров. FAQ описывает все три случая. Файл описывает себя сам (решение 5), поэтому имя объекта восстановлению не мешает.

Замена данных работающего инстанса тоже принимает только файл. Отвергнутый вариант для обоих случаев — выбор бэкапа из списка: на пустом инстансе через настройки хранилища, введённые на экране, на работающем через каталог. Для пустого инстанса каждому из восьми провайдеров, включая Google Drive, нужен список файлов по префиксу со сворачиванием частей S3, а экран без входа подключается к адресам, которые ввёл посетитель. Ради одного действия при переезде это слишком дорого. Для работающего инстанса выбор из каталога экономит одно скачивание файла, но требует перед перезапуском скачивать копию из хранилища на диск и отдельного правила для копии-источника при проверке копий после восстановления.

### 7. Восстановление выполняется при старте, до миграций и фоновых сервисов

Ядро восстановления запускается в `main` до `runMigrations`, если есть источник:

- подготовленный файл в `databasus-data/recovery/`, загруженный на экране первого запуска или root admin при замене данных;
- `RECOVERY_DUMP_PATH`, только если на инстансе нет аккаунтов.

Все источники — файлы на диске. Ядру не нужен доступ к хранилищам до миграций, а credentials хранилищ на диск не попадают.

Шаги ядра:

1. Прочитать ключ. В интерфейсе он подготовлен рядом с источником, в env-пути лежит в `secret.key`. Пробелы по краям отбросить. `SecretKeyService.GetSecretKey` (`backend/internal/features/encryption/secrets/service.go:52-81`) отдаёт файл ключа целиком, а `DeriveBackupKey` (`backend/internal/features/backups/backups/encryption/utils.go:31`) берёт `masterKey + backupID`. Поэтому на сервере с переводом строки в конце `secret.key` этот перевод строки входит в ключ каждого бэкапа. Кандидатами считаются обрезанный ключ, он же с `\n` и он же с `\r\n`.
2. Прочитать открытый блок метаданных в начале файла. Сравнить версию схемы goose с последней миграцией бинарника: бэкап со схемой новее отклоняется, и сообщение называет версию Databasus из блока. Сравнить major-версию PostgreSQL, с которой снят дамп, с версией сервера внутренней базы: бэкап с более новой major-версии отклоняется с сообщением, которое называет обе версии. Проверить ключ расшифровкой первого чанка: заголовок `PGRSUS01` содержит только магические байты, salt и nonce (`backend/internal/features/backups/backups/encryption/encrypting_writer.go:104-111`), поэтому неверный ключ виден только по провалу проверки подлинности GCM. Кандидаты проверяются по очереди, и дальше используется первый, который прошёл проверку.
3. Одной транзакцией удалить содержимое схемы `public` и восстановить бэкап. Сама схема не удаляется: на PostgreSQL 12–14 ею владеет суперпользователь, на 15+ — `pg_database_owner`, и роли внешней внутренней базы из `DATABASE_DSN` прав на `DROP SCHEMA` может не хватить. Миграции создают в `public` только таблицы, индексы и последовательности, поэтому транзакция начинается с `DROP TABLE ... CASCADE` для всех таблиц схемы по списку из `pg_tables`, включая таблицу версий goose, и `DROP SEQUENCE` для оставшихся последовательностей. Для этого достаточно владеть этими объектами, а ими роль владеет, потому что их создали её миграции. `pg_restore --no-owner --no-acl -f -` превращает файл в SQL, а из списка `pg_restore -l`, переданного через `-L`, убираются записи о самой схеме `public` и её комментарии. `psql --single-transaction -v ON_ERROR_STOP=1` выполняет удаление и этот SQL. `pg_restore` и `psql` берутся той же major-версии, что и сервер внутренней базы нового инстанса: такой `pg_restore` читает архивы всех более старых `pg_dump`, а его SQL этот сервер понимает. Более новые архивы отсекает шаг 2. PostgreSQL откатывает DDL вместе с транзакцией, поэтому при любой ошибке база остаётся прежней: пустой на новом инстансе и со старыми данными на работающем. В той же транзакции после SQL восстановления выполняются миграции, которых нет в бэкапе: ядро берёт из `./migrations` файлы с версией новее версии goose из блока метаданных и добавляет в поток сначала `RESET search_path`, потому что SQL от `pg_restore` начинается с `set_config('search_path', '', false)`, а миграции пишут имена таблиц без схемы, затем Up-часть каждого файла (текст между `-- +goose Up` и `-- +goose Down`) и строку в `goose_db_version`. psql сам разбирает операторы и dollar-кавычки, поэтому разметка `StatementBegin`/`StatementEnd` ему не нужна. Если падает миграция, откатывается всё, включая удаление старых таблиц. Так можно, потому что ни одна миграция не помечена `-- +goose NO TRANSACTION` и Go-миграций нет. Тест следит за этим, и новая миграция с такой пометкой сломает его с объяснением.
4. Записать в `secret.key` прошедший проверку кандидат байт в байт, через временный файл и `rename`. Так старые бэкапы баз, зашифрованные ключом с переводом строки, остаются расшифровываемыми, а `GetSecretKey` менять не нужно.
5. Удалить подготовленные файлы и записать результат в `databasus-data/recovery/result.json`.
6. Отдать управление обычному старту: `goose up`, которому уже нечего применять, затем шаги после восстановления (решение 9), затем фоновые сервисы.

Если восстановление упало, данные не тронуты. Ядро удаляет подготовленные файлы и пишет причину в `result.json`, чтобы следующий старт не повторял ту же ошибку. После успеха подготовленные файлы удаляются только после записи ключа. Если процесс оборвался между коммитом и записью ключа, файл остаётся на месте, и следующий старт восстанавливает его заново: шаг 3 снова удаляет содержимое схемы и восстанавливает его с нуля. Поэтому перед подготовленным файлом ядро аккаунты не проверяет. Гонку с регистрацией закрывает другое правило: пока подготовленный файл ждёт перезапуска, регистрация и эндпоинты восстановления без входа отвечают отказом.

Интерфейс сам ничего не восстанавливает. Он проверяет ключ и версию, чтобы сразу показать ошибку, готовит источник и завершает процесс кодом выхода 75. Больше нигде в `backend/cmd` этот код не используется: там только 0 и 1, а panic даёт 2. `docker/start.sh` на код 75 перезапускает приложение, не останавливая PostgreSQL. На любой другой код выхода контейнер, как и сейчас, завершается. Сейчас `handle_stop_signal` (`docker/start.sh:649-656`) шлёт сигнал по `application_pid`, поэтому цикл перезапуска обновляет `application_pid` для нового процесса, а сигнал, пришедший между выходом и новым запуском, отменяет перезапуск и останавливает PostgreSQL. Пока процесс перезапускается, интерфейс показывает индикатор восстановления и опрашивает эндпоинт результата. Когда сервер снова отвечает, интерфейс предлагает вход или показывает причину сбоя из `result.json`.

Отвергнутые варианты:

- **Восстановление внутри работающего процесса.** Фоновые сервисы уже запущены и могли бы начать бэкап или удаление по наполовину восстановленным конфигам. Кроме того, ключ закэширован, а GORM работает со схемой, которую меняют у него из-под ног.
- **Перезапуск силами `restart: unless-stopped`.** Он зависит от того, как оператор запустил контейнер.
- **Восстановление в соседнюю базу с переключением одной командой.** Одна транзакция даёт ту же гарантию «всё или ничего» без второй базы. Кроме того, роли внешней внутренней базы, заданной через `DATABASE_DSN`, может не хватить прав на `CREATE DATABASE`, а удаление объектов в шаге 3 требует только тех прав, которые уже нужны миграциям.
- **Отдельное удаление схемы, затем `pg_restore --single-transaction`.** Удаление коммитится раньше восстановления, и битый файл оставил бы работающий инстанс без данных.
- **Миграции после коммита восстановления, обычным `goose up` при старте.** Если миграция падает на старых данных, инстанс остаётся с восстановленной, но не мигрированной базой и не стартует, а у работающего инстанса прежних данных уже нет. Ценой одной транзакции становится правило «миграции без `NO TRANSACTION`», и его проверяет тест.

**Замена данных работающего инстанса.** Эндпоинт для root admin принимает загруженный файл бэкапа и необязательный ключ. Выбора из списка бэкапов инстанса нет: чтобы откатиться к своему бэкапу, root admin сначала скачивает его в той же секции. Пустой ключ означает текущий. Эндпоинт проверяет ключ, версию и свободное место так же, как экран первого запуска, готовит источник и завершает процесс тем же кодом выхода. Подтверждение — это диалог с предупреждением в интерфейсе (решение 8). Отдельной подтверждающей фразы в API нет.

Запись аудита о замене добавляется в шаге после миграций уже в восстановленную базу. Адрес root admin и время бэкапа берутся из подготовленного запроса. До перезапуска тот же факт пишется в лог сервера, потому что прежний журнал аудита удаляется вместе со схемой. Результат замены root admin видит через тот же эндпоинт результата, что и экран первого запуска.

Отвергнутый вариант — страховочный бэкап на диске сервера перед заменой и кнопка «отменить восстановление». Битый файл уже не трогает данные благодаря транзакции. Остаётся случай, когда root admin выбрал не тот бэкап, и для него хватает бэкапа этого инстанса, скачанного до замены: предупреждение об этом напоминает. Страховочный бэкап потребовал бы места на диске, правил, когда его удалять, и отдельной обработки неудачного возврата.

Загруженный файл лежит на диске до перезапуска. Это второе исключение из ADR-0004, по той же схеме, что и для `pg_restore -j`: перед приёмом файла проверяется свободное место. Исключение оформляется ADR вместе с решением восстанавливать Databasus через `pg_dump` и миграции.

### 8. Вместо паузы — предупреждение перед восстановлением

Восстановленный инстанс стартует как обычно: `runBackgroundTasks` запускает все фоновые сервисы, включая планировщики, retention и воркер удаления файлов. Если старый инстанс жив, оба пишут в одни хранилища и удаляют файлы друг друга. Защита от этого организационная. Экран первого запуска и диалог замены перед запуском показывают предупреждение: старый инстанс нужно выключить, бэкапы после времени создания этого бэкапа неизвестны, файлы LOCAL-хранилищ есть, только если перенесли папку данных. Время создания бэкапа берётся из открытого блока метаданных, его отдаёт эндпоинт проверки ключа и версии. При восстановлении через `RECOVERY_DUMP_PATH` то же предупреждение пишется в лог.

Отвергнутый вариант — режим паузы, в котором восстановленный инстанс не пишет в хранилища и не удаляет из них, пока администратор не подтвердит, что старый сервер выключен. Пришлось бы делить фоновые сервисы на две группы и запускать вторую по сигналу, отклонять ручные запуски в паузе, хранить флаг и показывать баннер. Подтверждение в паузе защищает так же организационно, как и предупреждение, только позже и дороже.

### 9. Состояние после восстановления

Шаги после миграций выполняются до старта фоновых сервисов:

- переводят физические цепочки в `CHAIN_BROKEN`, чтобы следующий физический бэкап был FULL;
- приводят запуск бэкапа Databasus, снявший этот бэкап, к завершённому. Источник — всегда файл, не связанный с копией, поэтому все копии запуска проверяются чтением открытого блока метаданных в начале их файлов через `GetFile`. Копия записана, только если файл найден и ID бэкапа в блоке совпадает. Если файла нет, ID другой или хранилище ответило ошибкой, копия неудачна с ошибкой запуска и без запроса на удаление файла;
- удаляют из `storage_pending_deletions` строки для файлов копий этого запуска. `Store.WriteFile` (`backend/internal/features/storages/files/store.go:56`) создаёт такую строку до первого байта, а снимает её только `ConfirmFileWrites`, поэтому у копий идущего запуска она есть в снимке. Для записанной копии удаление строки равно подтверждению записи, а файл непроверенной копии по правилу выше не удаляется;
- добавляют запись аудита о замене данных, если восстановление было заменой.

Бэкапы и восстановления, которые шли в момент снимка, помечают неудачными обычные проверки, которые каждый сервис делает при старте: `failBackupsInProgress` логического планировщика (`backend/internal/features/backups/backups/backuping/logical/scheduler.go:66,304`), `failClaimlessInProgressBackups` физического (`backend/internal/features/backups/backups/backuping/physical/scheduler.go:629-636`), `failRestoresInProgress` (`backend/internal/features/restores/restoring/scheduler.go:46,97`). Проверки бэкапов обрабатывает `reapStaleRuns` верификации (`backend/internal/features/verification/runs/scheduler.go:166-216`): агент из снимка давно не выходил на связь, поэтому `RequeueOrFail` (`runs/service.go:437-445`) снова ставит проверку в очередь, пока остались попытки, а потом помечает её неудачной. Фоновые сервисы стартуют сразу после шагов восстановления, поэтому отдельной пометки не нужно, а причины сбоя те же, что после обычного перезапуска.

Прерванные запуски бэкапа Databasus при обычном старте помечаются неудачными тем же способом, что и бэкапы баз. Шаг после восстановления выполняется раньше, поэтому запуск, снявший бэкап, получает проверку копий, а не пометку «прерван».

Остальные строки `storage_pending_deletions` из бэкапа остаются как есть и обрабатываются сразу после старта.

### 10. Ключ отдаёт отдельный эндпоинт, пока нет подтверждения

`GET` ключа и `POST` подтверждения доступны только root admin (`is_root_admin`) и только пока подтверждения нет. Фронтенд запрашивает состояние при каждом открытии приложения, а не только после входа, и показывает экран ключа поверх приложения. JWT хранится в localStorage, и root admin после обновления может ни разу не войти заново. Так экран работает одинаково после регистрации, после OAuth-редиректа, с уже открытой сессией и после обновления. Эндпоинт отдаёт ключ с отброшенными пробелами по краям, то есть то же значение, которое принимает восстановление.

Подтверждение хранится в новой однострочной таблице состояния инстанса. Отвергнутый вариант — `users_settings`: там политика пользователей, а не состояние инстанса.

Отвергнутый вариант — вернуть ключ в ответе `signup`. После OAuth-редиректа этот ответ фронтенд не видит, а обновлённые инстансы экран бы так и не показали.

### 11. Письма о сбоях идут через почту инстанса, когда хранилище или бэкап Databasus входит в сбой или выходит из него

У копии хранится вид ошибки: ошибка записи в хранилище или ошибка запуска. Ошибка записи — это ошибка, которую вернула загрузка в это хранилище, после чего раздача её отключила. Ошибка запуска — всё, что ломает запуск целиком: ошибка `pg_dump` или шифрования, версия вне 12–18, таймаут запуска и пометка «прерван перезапуском Databasus». Её же получает копия, которая не подтвердилась при проверке после восстановления (решение 9). Её получают все незаписанные копии запуска, а у версии вне диапазона копий нет вовсе, и причина лежит только в записи о запуске.

Из каталога выводятся два состояния:

- хранилище в сбое, когда три последние его копии с ошибкой записи идут подряд, а копии с ошибкой запуска пропускаются. Выходит из сбоя на первой записанной копии;
- бэкап Databasus в сбое, когда три последних запуска, не считая прерванных перезапуском, закончились ошибкой запуска. Выходит из сбоя на первом запуске хотя бы с одной записанной копией.

Без разделения ошибок сломанный `pg_dump` перевёл бы в сбой все хранилища, и администраторы получили бы письма о здоровом S3. Прерванные запуски пропускаются в обоих счётах, чтобы несколько обновлений подряд во время бэкапа не давали ложного письма. Они всё равно повторяются, поэтому бэкап после перезапуска не ждёт следующего срока.

После каждого запуска оба состояния сравниваются с состоянием до него. Письмо всем администраторам уходит только при входе в сбой и при выходе из него, через почту инстанса из спеки `outgoing-email`. Счёт идёт по копиям и запускам, а не по сериям повторов. Поэтому новое хранилище, которое не работает с первой копии, даёт письмо после третьей неудачной копии, а частое cron-расписание, при котором повтор не успевает начаться, всё равно не даёт письма на одиночный сбой. Предупреждение в интерфейсе берёт те же состояния.

Бэкап устарел, когда прошёл второй момент запуска по расписанию после последнего запуска хотя бы с одной записанной копией. Готового кода для этого нет: планировщик спрашивает только булево `Interval.ShouldTriggerBackup(now, lastBackupTime)` (`backend/internal/features/intervals/model.go:72`), а `ApproxPeriod` для cron возвращает 0. Поэтому в `intervals` пишется новая функция «следующий момент запуска после времени t». Для cron она использует `schedule.Next`, для остальных видов — их правила времени суток, дня недели и дня месяца. Устаревание проверяется как `next(next(lastWrittenRun)) <= now`. Если записанных запусков ещё не было, вместо `lastWrittenRun` берётся время создания строки настроек бэкапа Databasus, то есть установки или обновления до версии с этой возможностью. Отвергнутый вариант — удвоенный промежуток между прошлыми моментами запуска: robfig/cron умеет идти только вперёд.

Повторы из решения 5 делают так, что при часовом расписании три неудачные попытки набираются примерно за 10 минут, а не за три часа. Одиночный сбой исправляет повтор, и до администратора он не доходит. Отвергнутые варианты — письмо на каждый сбой, при часовом расписании это 24 письма в сутки, и письмо после первой неудачной копии: короткий сбой S3 давал бы пару писем «сбой» и «восстановление» на пустом месте.

## Risks / Trade-offs

- [Внутренняя база растёт на одну строку на каждый WAL-сегмент, и дамп может стать большим] → В списке показывается размер, по умолчанию действует GFS-retention, а предупреждение о LOCAL-хранилище напоминает, что дампы лежат на том же диске.
- [Снимок внутренней базы держится, пока идёт самая медленная загрузка] → Запуск ограничен таймаутом, а упавшая загрузка отключается от раздачи и не тормозит остальные.
- [Между шагами восстановления на диске лежат ключ и файл бэкапа] → Файлы в `databasus-data/recovery/` с правами 0600 удаляются после попытки, удачной или нет. Credentials хранилищ на диск не попадают, потому что ядро читает только файлы.
- [Копия, которую после восстановления не удалось проверить из-за недоступного хранилища, считается неудачной, хотя файл может существовать] → Файл не удаляется и остаётся в хранилище без записи в каталоге. Вернуть его могла бы только сверка, а она вне рамок изменения. У запуска обычно есть другая проверенная копия, а следующие запуски создают новые.
- [Старый инстанс продолжает работать после восстановления] → Два инстанса пишут бэкапы в одни хранилища и удаляют файлы друг друга. Защита только организационная: предупреждение перед восстановлением и запись в лог при восстановлении через переменную окружения.
- [Воркер удаления нового инстанса может стереть файл, запись которого старый сервер подтвердил уже после снимка] → Новый каталог такой файл всё равно не знает. Вернуть его могла бы только сверка, а она вне рамок изменения.
- [Бэкапы и WAL после снимка новому инстансу неизвестны, PITR возможен только до времени снимка] → Предупреждение перед восстановлением показывает время создания бэкапа. Окно сокращается часовым расписанием.
- [Root admin заменяет данные не тем бэкапом и теряет свой аккаунт] → Отменить замену нельзя. Предупреждение говорит, что войти нужно будет аккаунтом из бэкапа, и советует заранее скачать бэкап текущего инстанса: заменой из него возвращаются прежние данные.
- [Перевод хранилища в инстанс отнимает у владельца воркспейса право редактировать своё хранилище] → Перевод делает только администратор инстанса, после предупреждения, что обратного пути нет.
- [Код перезапуска зависит от `docker/start.sh`] → Helm использует тот же образ. Если процесс запущен без `start.sh`, он просто завершается, и восстановление выполнится при следующем ручном запуске.

## Migration Plan

1. Миграции: тип `workspace_id` у хранилищ остаётся nullable, добавляются настройки ролей хранилища и таблица доступа воркспейсов, таблицы бэкапов Databasus и их настроек, таблица состояния инстанса и LOCAL-хранилище инстанса по умолчанию.
2. Первый бэкап Databasus после обновления делается по расписанию, в течение часа.
3. Root admin видит экран ключа при следующем входе.

Откат на предыдущую версию со схемой новой версии не поддерживается, как и для любой другой миграции. Down-миграции удаляют новые таблицы и хранилища инстанса, а `workspace_id` у оставшихся хранилищ не трогают.
